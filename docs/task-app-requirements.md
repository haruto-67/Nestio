# Nestio 要件定義書 (v0.2)

## 1. 背景・目的

- タスク / サブタスク / 期限が頭の中でごちゃごちゃになってきたので整理したい
- 以前 TickTick を使っており概ね満足していたが、有料である点とカスタマイズ性から自作へ
- 一旦 TickTick 相当を目指すが、仕様を TickTick に縛られない
- **ランニングコストは可能な限りゼロ**

## 2. 前提・制約

| 項目 | 決定 |
|---|---|
| 対象デバイス | iOS / iPad / PC ブラウザ（Mac・Windows） |
| 配布形態 | **PWA 一本**（ネイティブ化は将来判断） |
| 認証 | Google ログインのみ |
| 開発機 | MacBook |
| ホスティング | Raspberry Pi 5（既存 Minecraft サーバーと同居）／Docker |
| ドメイン | `nestio.niwatorimc.com`（サブドメイン分離） |
| 予算 | 0円（Apple Developer Program・Claude API 課金なし） |

### なぜ PWA か
- iOS ネイティブは Apple Developer Program（年 99 USD）が必須。「無料」要件と両立しない
- PWA なら「ホーム画面に追加」でアプリ同様の見た目・起動が得られ、iOS 16.4+ で Web Push も通る
- Sign in with Apple も同 Program が前提のため、認証は Google のみとする（Google OAuth は無料）

### なぜラズパイか
- Oracle Cloud Always Free は 7 日間アイドル判定でインスタンス回収される規約があり、A1 ARM は日本リージョンで枯渇しがち（Pay As You Go 化すれば回収対象外にできるが不確実性が残る）
- MacBook 常時稼働は、開発機と本番の同居・OS アップデートによる再起動・スリープ制御・外部公開の手間からリスクが高い
- 本アプリの実体は API + DB のみで 1 ユーザーなら 200〜300MB 程度。既存の nginx / ドメイン / MySQL を再利用できる
- **Docker Compose で組んでおけば、後からクラウドへ移すのは compose ごと移動するだけ**

## 3. 機能要件

### 3.1 タスク管理（コア）

- **リスト / フォルダ**による階層分け
- **タグ**（複数付与可）
- **優先度**（なし / 低 / 中 / 高）
- **期限**（日付のみ / 日時指定）
- **繰り返しタスク**
- **サブタスク：無制限ネスト**
- メイン画面は**リスト表示**

#### 繰り返しの仕様
- 表現形式は **RRULE (RFC 5545)** を採用
  - 「毎週火木」「毎月最終金曜」等を独自形式で持つと必ず破綻するため
  - そのまま ICS に流用でき、カレンダー連携が実質タダで完成する
- **遅れて完了しても次回期限は元の予定日基準**（`dtstart` をズラさず次の occurrence を取る）
- **サボった分は溜めない**：未完了の過去 occurrence は生成せず、常に直近 1 件のみ表示してスキップ

#### 親子関係の仕様
- **子タスクが全て完了するまで親タスクを完了できない**
  - UI：未完了の子がある間は親のチェックボックスを disable
  - 無制限ネストのため判定は再帰的に行う
  - 同期の結果として矛盾（親が完了済みなのに子が未完了）が生じた場合、サーバー側で親を未完了へ戻す

### 3.2 表示・ソート

#### ソート
ユーザーが切り替え可能なソート順を提供する。

| モード | 仕様 |
|---|---|
| カスタム | 手動並び替え（`sort_order`）。デフォルト |
| 期限順 | 期限なしは末尾へ（`ORDER BY due_at IS NULL, due_at`。SQLite は NULL が先頭に来るため明示が必要） |
| 優先度順 | 高 → 低。「なし」(0) は末尾 |
| 名前順 | **自然順ソート**を使用 |

- 名前順は「01. 〜」のようなインデックス付き運用を想定するため、単純な文字列比較では `10` が `2` より前に来てしまう
- クライアント側で `Intl.Collator(undefined, { numeric: true })` を用いて自然順に並べる
- ソート順はリストごとに記憶する

#### スマートリスト
実テーブルを持たず、動的クエリで生成する。

- 今日 / 明日 / 今週 / 期限なし / 全て / 完了済み
- ユーザー定義のカスタムスマートリストは将来拡張とする

#### 期限切れの繰り越し
- 期限を過ぎた未完了タスクは「今日」ビューに繰り越して表示する
- **`due_at` の実データは書き換えない**（表示上の繰り越しに留める）
  - 実データを動かすと繰り返しタスクの occurrence 計算と実績ログが壊れるため
- UI 上は「期限切れ」セクションとして当日分と区別して表示

### 3.3 メモ機能

- タスクとは**完全に別物**として扱う（別テーブル・別画面）
- Windows / Mac の「付箋」の OS 横断版という位置づけ
- タイトル + 本文 + 色 + ピン留め程度のシンプルな構成

### 3.4 ポモドーロタイマー

**おまけ機能**の位置づけ。タイマーが鳴れば良い。

- 25分 / 5分などの基本サイクル
- タスクに紐付け可能（紐付けなしでも動く）
- **実績記録は行わない**。累計時間の集計や実績ビューは対象外
- サイクル設定の柔軟性も最小限で良い
- 終了通知は**サーバー側にプッシュを予約**して送る
  - Service Worker のバックグラウンドタイマーはブラウザに停止されるため信頼できない

### 3.5 検索

- **SQLite の FTS5** を使用し、タスクのタイトル・本文およびメモを全文検索の対象とする
- **`trigram` トークナイザを指定する**
  - FTS5 の標準トークナイザは日本語の分かち書きに対応しておらず、指定しないと日本語がほぼ引っかからない
- タスク・メモを横断して検索できる UI とする

### 3.6 添付ファイル

MVP から画像添付に対応する。タスク・メモの両方に添付可能。

**保存方式**
- バイナリは SQLite の BLOB ではなく**ファイルシステム上に保存**し、DB にはメタデータのみ持つ
- ファイル名は内容の SHA-256（content-addressed）とする
  - 同一画像の重複保存を防げる
  - 内容が不変になるためキャッシュと同期の扱いが単純になる

```
attachments : id, user_id, owner_type(task|note), owner_id,
              sha256, filename, mime, bytes, width, height,
              created_at, deleted_at
```

**アップロード前の圧縮（必須）**
- iPhone の写真は 1 枚 3〜5MB あり、そのまま保存すると Pi のディスクとバックアップ容量を圧迫する
- **クライアント側で canvas を通して長辺 1600px 程度・WebP または JPEG に変換**してから送信する
- iOS は HEIC で出力するため、この変換をクライアントで行えばサーバー側に変換処理が不要になる
- 1 ファイルあたりの上限サイズと、ユーザーあたりの総容量上限を設ける

**オフライン時の扱い**
- 画像は IndexedDB に Blob として保持し、outbox 経由でオンライン復帰時にアップロード
- 添付レコードは他テーブルと同じ LWW で同期
- **バイナリ自体は不変なので衝突が発生しない**（content-addressed の利点）

**配信とアクセス制御**
- 画像ディレクトリを nginx で直接公開しない（他人の添付が URL 推測で見られる）
- API がセッションを検証し、`X-Accel-Redirect` で nginx に実ファイル配信を委譲する

**削除**
- 論理削除後、参照カウントがゼロになったファイルのみ cron で物理削除
- content-addressed のため、複数レコードから同一ファイルが参照される点に注意

### 3.7 同期 / オフライン対応

**ローカルファースト構成**を採用する。

1. クライアントは IndexedDB を「正」として動作（オフラインでも即応）
2. 変更は **outbox キュー**に積み、オンライン復帰時にサーバーへ送信
3. 全レコードに `updated_at` / `deleted_at`（論理削除）を保持
4. 衝突解決は**フィールド単位の Last-Write-Wins**
   - 1 ユーザー・複数デバイス用途なら CRDT は過剰
   - メモ本文のみ同時編集で片方が消える可能性 → 衝突コピーを残す運用でカバー
5. サーバーからの差分配信は **SSE**（再読み込み不要の要件を同時に満たす）

**要注意**：`parent_id` 更新時は祖先チェックを必ず入れる。
デバイス A で「X を Y の下へ」、デバイス B で「Y を X の下へ」が同時に起きると循環参照が生じ、再帰クエリが無限ループする。

### 3.8 通知

- 期限リマインダー / ポモドーロ終了の**両方**
- Web Push (VAPID) を使用 — 自前鍵なので**無料、Apple Developer Program 不要**
- iOS では「ホーム画面に追加」済みの場合のみ有効（要ユーザー案内）

### 3.9 カレンダー連携

- **第一段階：読み取り専用の ICS フィード配信**
  - 推測不能なトークン付き URL を発行し、Google カレンダー / Apple カレンダーから購読
  - RRULE をそのまま出力できるため実装コスト最小
- 第二段階（任意）：Google Calendar API による双方向同期（無料枠内）

### 3.10 MCP 連携

**認証は OAuth 2.1（Authorization Code + PKCE）とする**
- Claude のリモート MCP コネクタは固定 Bearer トークンでは接続できず、OAuth ベースの認可を要求する（過去の自作 MCP での実体験に基づく）
- Nestio 自身が簡易 OAuth 認可サーバーとして振る舞い、「Claude が接続 → Nestio の認可画面 → 許可で利用可能」という流れにする
- Google ログイン（A-1）とは別レイヤーの認可であることに注意
- 発行するアクセストークンはハッシュ化して保存し、有効期限とスコープ（read / write）を持たせる

**権限：読み書き＋トリガー実行**

- 既存の `niwatorimc.com/mcp` と同様、HTTP 型 MCP サーバーとして実装
- 提供ツール例：`list_tasks` / `search_tasks` / `create_task` / `complete_task` / `list_notes`
- 「期限の近いタスクは？」等を Claude チャットから直接聞ける

#### トリガー機能（アプリ → Claude Code CLI）
- タスク完了などのイベントを起点に、ラズパイ上の `claude -p` を実行
- Claude API ではなくサブスクリプション経由の CLI を叩くため追加課金なし

#### トリガー（Hatch）の候補定義

**イベント（発火条件）**

| イベント | 用途例 |
|---|---|
| タスク完了 | 最も基本。リスト / タグ / 優先度でフィルタ可能 |
| リスト内の全タスク完了 | プロジェクト完了の検知 |
| 期限の N 分前 | 事前準備の自動化 |
| 期限超過 | 放置タスクの掘り起こし |
| タスク作成時 | 受け取った直後に整形・分解 |
| 繰り返しタスクの新規発生 | 定例作業の準備 |
| 毎日 / 毎週の指定時刻 | イベント非依存の定期実行 |

**アクション（ホワイトリスト方式・実装候補）**

| キー | 内容 |
|---|---|
| `claude_prompt` | 定型プロンプトを `claude -p` で実行し、結果をタスクのメモへ追記または通知 |
| `claude_subtasks` | タスク名を渡してサブタスク案を生成させ、子タスクとして追加 |
| `claude_summarize` | 完了したリストの内容を要約してメモに残す |
| `create_task` | テンプレートから別タスクを自動生成 |
| `create_note` | メモを自動生成 |
| `add_tag` / `set_priority` / `move_to_list` | アプリ内部の操作のみ（外部実行なしで安全） |
| `push_notify` | 自分宛に Web Push |
| `discord_notify` | 既存の Discord Bot / Webhook へ通知 |
| `run_registered_script` | 事前登録済みスクリプトを ID 指定で実行（Minecraft サーバーのバックアップ、RCON コマンド送信など） |

**実行モデル**
- `claude -p` は数十秒かかるため**必ず非同期**。ジョブキューに積んで順次実行する
- 同時実行数は 1 に制限（Pi のリソース保護）
- タイムアウトとリトライ上限を設定し、実行ログを必ず保存する
- **ループ防止**：トリガー起因で発生した変更にはフラグを立て、そこから再度トリガーを発火させない
  - これがないと「Claude がタスク生成 → トリガー発火 → また生成」で無限ループする

**セキュリティ要件（必須）**
- 実行可能なアクションは**ホワイトリスト方式で事前定義**する。ユーザー入力をそのままコマンドに渡さない
- プロンプトはテンプレート化し、変数部分のみ差し込む
- 専用の低権限ユーザーで実行し、作業ディレクトリを限定
- `--allowedTools` で使用可能ツールを絞る
- 実行ログを必ず残す

### 3.11 ゴミ箱

- 全テーブルが `deleted_at` による論理削除のため、ゴミ箱は追加コストなく実現できる
- **保持期間は 30 日**。経過後に cron で物理削除する
- 物理削除しないとオフライン同期用の墓標（tombstone）が無限に増えるため、削除処理は必須
- 添付ファイルは参照カウントがゼロになったもののみ実体を削除

### 3.12 UI / 外観

- TickTick 風の 2 ペイン構成
  - 左：フォルダ → リストのツリー（iPhone 幅ではドロワーに格納）
  - 右：タスク一覧。上部にタグ・優先度のフィルタバー
- **ダークモード / ライトモードの切替のみ**対応（テーマ自体の自作は不要）
- iPad は横向きでそのまま 2 ペインが活きる

### 3.13 キーボードショートカット

PC ブラウザでの操作効率のため、ショートカットを標準で用意し、**キー割り当てをユーザーがカスタマイズできる**ようにする。

**デフォルト割り当て（案）**

| 操作 | 既定キー |
|---|---|
| クイック追加（Egg） | `N` |
| 検索 | `/` または `Cmd/Ctrl + K` |
| 選択中タスクを完了 | `Space` または `X` |
| 上下移動 | `J` / `K` |
| サブタスクにする / 戻す | `Tab` / `Shift + Tab` |
| 優先度を上げ下げ | `1` 〜 `4` |
| 削除 | `Delete` |
| 「今日」ビューへ（Roost） | `G` → `T` |
| ダーク / ライト切替 | `Cmd/Ctrl + Shift + L` |
| ショートカット一覧を表示 | `?` |

**要件**
- 割り当ては設定画面で変更でき、ユーザーごとに保存・同期する
- 割り当ては `keymap` として `/sync` の対象に含める（全デバイスで共通の操作感）
- 入力欄にフォーカスがある間はショートカットを無効化する（誤爆防止）
- 競合する割り当ては設定画面で警告する
- `?` で現在のキーマップを一覧表示する

### 3.14 セキュリティ

自分専用アプリだが、公開ドメインに置く以上の最低限を満たす。実害の大きい順。

**通信・認証**
- 全通信を HTTPS に限定。nginx で **TLS 1.2 以上のみ許可、HSTS、OCSP Stapling** を設定（Phase 6）
- セッションは httpOnly / Secure / **SameSite=Strict** Cookie。localStorage にトークンを置かない
  - `SameSite=Strict` により、外部サイトからの偽装リクエスト（CSRF）でセッションが使われるのを防ぐ
- Google OAuth は state + PKCE で認可コード横取りを防止
- **`email_verified` を検証**してからユーザーを作成 / 参照する

**レート制限（実装対象）**
- `/sync/push`、`/auth/*`、`/mcp`、`/attachments/*` にユーザー / IP 単位のレート制限を掛ける
- バグや暴走クライアントによる大量リクエストで Pi が詰まるのを防ぐ

**添付ファイル**
- クライアント申告の Content-Type を信用しない。**マジックバイトで実体の形式を検証**する
- 許可する形式を画像のみに限定
- 配信時は `Content-Disposition` と `X-Content-Type-Options: nosniff` を付け、ブラウザの Content-Sniffing による実行を防ぐ

**MCP トークン**
- 3.10 の通り OAuth 発行。トークンはハッシュ化保存・有効期限・スコープ制限・失効機能を持たせる

**Hatch（コマンド実行）**
- 3.10 のホワイトリスト・`execFile`（`shell:true` 禁止）・低権限ユーザー・作業ディレクトリ限定を厳守

### 3.15 エラーログ / 可観測性

障害の原因を後から追えるようにする。**外部 SaaS は使わず、ログファイルに書き出して自分で見に行く**方式。通知は行わない。

**サーバー側（構造化ログ）**
- 構造化 JSON（1 行 1 イベント）。pino を想定
- 全リクエストに `request_id` を発番し、そのリクエストの処理・エラーを串刺しで追える
- 例外は**スタックトレース付き**で記録
- 記録対象：未処理例外 / API エラー応答（4xx・5xx）/ `sync/push` の reject 理由（循環参照・親子矛盾・冪等スキップ等）/ push 送信失敗 / DB エラー
- **Hatch の実行ログ**：`trigger_runs` に加え、`claude -p` の stdout / stderr 全文をファイルにも残す
- ログレベル：`error` 常時 / `info` 既定 / `debug` は `.env` で切替
- **ローテーション**：日次分割、`LOG_RETENTION_DAYS`（既定 14 日）で自動削除。ログでディスクを埋めない
- 出力先：`/var/lib/nestio/logs/`（named volume）。**トークン・Cookie 等の秘密情報はマスク**して出力

**クライアント側（同期の復旧に必須）**
- オフライン同期は端末内で壊れると原因が見えないため、端末側にもリングバッファでログを保持
- 記録対象：outbox の送信失敗 / `full_resync_required` の発生 / 衝突解決の結果 / SSE 切断・再接続
- `POST /api/v1/client-logs` で端末ログをサーバーへ送れる。設定画面から手動送信

**閲覧**
- 自分専用の簡易ログビューア（直近エラーを時系列表示、`request_id` で絞り込み）
- または `tail` / `jq` で直接見る運用でも可（構造化 JSON なので整形しやすい）

### 3.17 ネーミングと世界観

アプリ名は **Nestio**（nest = 巣 + io = 情報の入出力口）。

巣・卵をモチーフにした語彙（Nest / Egg / Hatch / Roost）を世界観として持つが、
**初見での分かりにくさを避けるため、既存の呼び名がある機能は一般名詞のまま据え置く**。

| 方針 | 対象 |
|---|---|
| 一般名詞のまま | タスク / リスト / フォルダ / タグ / 完了 / 今日 / メモ など、他アプリで名前が定着しているもの |
| 世界観の語を当てる | 既存の呼び名がなく命名の自由度が高いもの、および装飾レイヤー |

**世界観を出す場所**
- **Hatch** … トリガー機能の名称。新規性のある機能で既存の呼び名がなく、「完了を起点に何かが動き出す＝孵化」と意味も一致する
- **Egg** … クイック追加のアイコン・空状態のモチーフ（ラベル自体は「追加」のまま）
- **Roost** … 「今日」ビューのアイコンや空状態の文言（ラベルは「今日」のまま）
- アプリアイコン、空状態のイラストと文言、通知の言い回し、テーマ名、リリースのコードネーム

機能名を世界観の語に置き換えると操作の推測が効かなくなるため、
**語彙は「装飾」に置き、「ナビゲーション」には置かない**ことを原則とする。

## 7. インフラ・運用

### 7.1 データベース（SQLite）

MySQL は現在停止中であり、本アプリのために起こし直すと常駐で 300〜400MB を消費する。
SQLite なら**別プロセスが常駐しない**ため、Pi のメモリ状況に対して最適。
1 ユーザー・数デバイスの用途では SQLite が苦手とする「複数プロセスからの並行書き込み」に該当しない。
無制限ネストで使う `WITH RECURSIVE` にも対応している。

**初期設定（必須）**

| 設定 | 理由 |
|---|---|
| `PRAGMA journal_mode=WAL` | デフォルトの rollback journal だと書き込み中に読み込みが全ブロックされる |
| `PRAGMA busy_timeout=5000` | `SQLITE_BUSY` の握り潰しを防ぐ |
| `PRAGMA foreign_keys=ON` | SQLite はデフォルトで外部キー制約が無効 |
| STRICT テーブルを使用 | 型宣言が通常は無視されるため、指定しないと数値カラムに文字列が入る |

**日時の扱い**
- ISO8601 の TEXT か Unix epoch の INTEGER に**統一する**
- SQLite に DATE 型は存在しないため、事前に決めておかないと後で破綻する

**配置に関する制約**
- **DB ファイルを rclone マウント上に置かない**（ネットワーク FS はロックが壊れ DB が破損する）
- ローカル HDD 上に配置し、バックアップのみ rclone 経由で外部へ送る
- Docker で動かす場合は named volume か bind mount に出す（コンテナ内に置くと作り直しで消える）

**バックアップ構想**
- cron で `sqlite3 tasks.db ".backup /path/backup.db"` を実行し、既存の rclone Dropbox / Google Drive マウントへ転送
- 秒単位の継続レプリケーションが欲しくなった場合は Litestream を導入
- 将来 Postgres へ移行する可能性はあるが、スキーマが単純なうちは移行コストは低い

### 7.2 コンテナ運用

Linux コンテナは名前空間と cgroup の分離のみで、VM のような仮想化オーバーヘッドはない。CPU コストは誤差レベル。

**増加するリソース**
- `dockerd` + `containerd` の常駐で合計 100〜150MB
- コンテナごとの shim が数MB
- bridge ネットワークは NAT 経由のため若干のオーバーヘッド（`network_mode: host` で解消可）
- ARM64 イメージのディスク消費（数百MB）

固定で約 150MB を要するが、Lobby の `-Xmx` を 6G → 5G にすれば吸収できる範囲。

**セキュリティ上の必須事項**
- Docker は iptables を直接書き換えるため **ufw のルールを貫通する**
- ポート公開は必ず `127.0.0.1:3000:3000` の形でループバックにバインドし、nginx からリバースプロキシする
- `-p 3000:3000` と書くと、ufw で塞いだつもりのポートが外部から到達可能になる

**代替案**
- 常駐分をさらに削りたい場合は **Podman**（デーモンレス、待機時メモリ実質ゼロ、`podman-compose` で compose ファイルをほぼ流用可）
- 最軽量は素の systemd ユニット。既存の systemd + tmux 運用と一貫するが、「移植しやすさ」という当初の動機は薄れる
